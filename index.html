Reference Layer

Methodology

Deep reference

This is the long-form explanation of how the dashboard turns raw data into scouting, portal, value, and tournament outputs. Use the Help drawer for quick page-specific guidance, then come here when you want the full logic.

Data sources Perf and valuation logic Portal methodology Simulation stack
How to use it
Open this page when you need confidence in the assumptions behind a model output. It is the deep-dive reference for staff who want to understand where the numbers come from and what the caveats are.
Data Sources

MBB - Player stats come from the College Basketball Data (CBD) API through the worker. The dashboard keeps CBD as the source of truth for MBB performance data, while ESPN is used only as a supplement for roster bio details like height when a clean match is available.

WBB - Player stats come from ESPN's WBB by-athlete endpoints, with conference mapping, team context, and roster enrichment layered on top. Historical seasons are supported through the season picker, but older ESPN roster coverage can be thinner than current-season coverage.

Derived WBB metrics - eFG%, TS%, and A/TO are derived from the available box-score data. Stats ESPN does not provide cleanly for WBB, like BPM or WS/40, are removed from WBB scoring rather than fabricated.

The dashboard intentionally prefers stable primary data for player performance, then adds worker- or ESPN-based enrichment only where it improves context without replacing the core stat source.

PerfScore

PerfScore is the main player evaluation score. Each active stat is normalized between your configured Min and Max, weighted by your selected stat weight, then rolled into one composite score.

Formula: PerfScore = sum(weight x normalized stat) / sum(active weights)

Higher-is-better stats, like points or assists, reward strong raw values. Lower-is-better stats, like turnovers, are inverted automatically so a better underlying performance still scores higher.

PerfScore is always calculated inside the current league and position bucket, so guards are only compared with guards and bigs are only compared with bigs.

Valuation

Player valuation converts PerfScore into a market-style dollar estimate using an exponential curve anchored to your chosen Average Pay and Star Value.

k = ln(starValue / avgPay) / (starPerf - avgPerf)
Predicted = clamp(minPay, maxPay, avgPay x exp(k x (PerfScore - avgPerf)))

A minutes adjustment keeps tiny-sample or low-minute players from inflating too easily, and the conference multiplier can optionally move valuations up or down based on league context before the market curve is applied.

Evaluation presets simply save these choices - weights, min/max settings, valuation anchors, and conference multipliers - so different staff users can bring their own lens without changing the system default.

Position Groups

For percentile calculations, the dashboard buckets players into two broad role groups:

  • Guards - G, G-F
  • Bigs - F, C, F-C, C-F

This keeps comparison logic more honest. A guard is not graded against a rim-protecting center, and a big is not graded against a primary ball handler.

Role Tags and Similarity

Role tags are shorthand labels built from percentile thresholds across the core stats. Players can carry multiple tags at once if their profile supports it.

  • Elite Scorer - high scoring percentile
  • Floor General - passing and ball-security profile
  • 3-and-D - perimeter shooting plus defensive activity
  • Rim Anchor - rim protection and glass impact
  • Stretch Big - frontcourt shooting gravity

These tags make profiles easier to scan and also help the dashboard group similar player types more intelligently.

Team Hub and Team Builder

Team Hub is the real-team workspace. It uses actual team ratings, four factors, schedule context, and matchup data to scout a real roster or opponent.

Team Builder is the hypothetical workspace that now lives under Team Hub. It applies budget, player-cap, and roster-balance constraints so staff can build scenarios without overwriting the real-team view.

The recommended-fit logic in Team Builder is driven by the weakest percentile categories on the built roster, so the tool is solving gaps rather than just listing the highest-rated players.

Head-to-Head and Opponent Builder extend that scenario workflow by comparing category edges and letting staff build the other side of the matchup directly.

Transfer Portal

The Transfer Portal page is a scouting board, not just a raw feed. On the MBB side, the worker can merge normalized portal data from 247Sports and On3 with backend caching. On the WBB side, the live portal source currently comes from On3.

Portal entrants are matched back to the loaded player pool with normalized name and team logic so the board can surface class, Perf, valuation, and profile links whenever a confident match exists.

Portal Fit Lab ranks replacement targets by team context, outgoing-player needs, category priorities, and player value/performance. The goal is to answer "who best solves this actual roster problem?" rather than only "who is the best player in the portal?" The WBB board currently uses the On3 source only, while the MBB board can merge On3 with the cached 247 workflow.

Value Lab

Value Lab is an independent case-based investment workspace. Each case has its own roster, budget, actual contract entries, and saved business readout.

Model Value is the dashboard's internal estimate. Actual Spend is the real contract number you enter. If a contract is unknown, planning math falls back to model value so the case still works before every deal is final.

ROI Call compares player performance against the expected return for that spend tier. The labels run from Steal and Premium worth it on the positive side to Rich and Overpay on the negative side.

Outcome vs Spend looks for a dominant real-team context when it can, then maps roster Perf back into projected team strength and schedule wins so the business side can see what that spend profile is likely buying.

Compare Mode stacks the active case against another saved case from the same league and season. It surfaces which build is stronger on budget room, performance efficiency, projected wins, and roster turnover so staff can make cleaner business decisions.

Portal Value Watch extends the same lens to available portal options, highlighting players who look attractive from a bang-for-buck perspective.

AI Workflows

AI is used as an interpretation layer on top of dashboard data, not as a replacement for the underlying calculations.

  • Scout AI can query players, rosters, team context, and approved tool actions inside the dashboard.
  • Portal AI explains target boards and replacement fits after the portal model has already ranked the options.
  • Director AI Brief in Value Lab uses Gemini 2.5 Flash Lite, can compare two saved cases side by side, and supports PDF export for executive review.
  • War Room AI explains bracket simulation outputs after the tournament model finishes running.

The dashboard's preferred order is numbers first, AI second: the model produces the metrics, then Gemini turns those metrics into clearer staff-facing recommendations.

WBB Defaults

WBB uses its own default weights and min/max ranges because the stat environment is different from MBB. The scoring model is not a direct copy-paste from the men's side.

Guards lean more heavily on playmaking efficiency, defensive activity, and balanced shooting context. Bigs lean more heavily on rebounding, rim impact, and efficient frontcourt finishing.

Draft Radar remains MBB-only. WBB player evaluation still uses the same dashboard structure, but not every MBB-specific downstream model is carried over.

Simulation Stack

Teams Hub Monte Carlo runs single-game simulations from adjusted team strength, pace, matchup effects, recency form, and team-specific volatility. Regulation ties trigger overtime logic instead of ending as ties.

Tournament War Room uses a related bracket model, but applies it across the full field: play-ins resolve first, then each round is simulated repeatedly to estimate champion odds, Final Four odds, region winners, and common upsets.

The bracket model blends baseline offensive and defensive strength with four-factor matchup adjustments, recent form, and team-level volatility, then repeats the tournament thousands of times to measure advancement probabilities instead of pretending one path is certain.

Draft Radar

Draft Radar predicts MBB draft probability from college production using a sign-constrained elastic-net logistic regression model trained on recent draft classes and their undrafted comparison pool.

The strongest signals in the model come from conference tier, WS/40, class/age signal, rim-protection indicators, rebounding, and shooting efficiency. The system intentionally favors recall so likely draftable profiles are not missed too easily.

It is still a college-stat model, not a full NBA scouting stack. Physical tools, combine performance, team need, international context, and long-term projection all sit outside this model.
